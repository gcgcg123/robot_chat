## A2. 语料实测

| 指标 | 值 |
|---|---|
| 正文规模 | 864 行、约 2 万字、422 段（中位数 25 字） |
| 标题层级 | `#`×1、`##`×2、`###`×4、`####`×20、`#####`×30 |
| 页码锚点 | 55 个 `<sub>pN</sub>`（31 页）→ 可直接标出处 |
| 图表 | 4 张图 + 3 条图注、9 行表格 |
| 语言 | 简体（Dashboard / 回复为繁体，需处理） |
| 估算 chunk | 约 31 个（@600 字） |

结论：不引入向量数据库、不用 RAGFlow、不上 cross-encoder。31 个向量暴力余弦是微秒级，SQLite 存 blob 已足够。对照：全塞进提示词约 12k tokens 也做得到，但那是「只有一本手册」的解法，加第二本即崩、每轮烧 token、且无法说「书上没写」。

## A3. 建议架构（与 memory 系统分开）

```
data/knowledge/profiles/*.json    ← 每份文档一份清洗 profile（见 A8.1；无 profile 拒绝导入）
data/knowledge/**/*.md            ← 手工整理的场景问答走同一条导入路径
data/RAG_data/md/*.md             ← 原始语料（当前语料由 scripts/pdf_to_md.py 生成，视为冻结产物）
      │  scripts/import-knowledge.py   ← 解析→按 profile 过滤→切分→嵌入→落库（幂等、可 --dry-run）
      ▼
SQLite: knowledge_documents   (doc_id, path, sha256, cleaner_version, pages, chunk_count, imported_at)
        knowledge_chunks      (chunk_id, doc_id, ord, kind, section_path, page, text,
                               embedding, hits, created_at)   ← migration v6
                               kind = 'scenario' | 'reference'（两档门槛，见 A8.2）
      ▼
services/knowledge/retriever.py   ← hybrid 检索（向量 + 字面），段数超阈值时改用 mmap（见 A8.3）
      ▼
create_app(providers={"rag": KnowledgeProvider(...)})
      ▼
pipeline._provider_chunks() → [不可信参考 手册 p7 › 二、沟通的因素] …
```

**为何不复用 `memory_chunks`（owner_user_id IS NULL 当共享知识）**：飞轮的 slot/hot/cold 升降级、衰减、hits 提升对静态语料无意义；`MAX_CANDIDATES=500` 与 32 槽位会被语料挤占；删一本文档要能级联删 chunk。分离更干净（代价：多一张表 + 一次 migration）。

## A4. 关键设计点

**① 只靠向量会漏。** 已实测：中文「问题 vs 陈述句」余弦最差间距仅 0.001（无鉴别力），「问题 vs 标准问句（probe）」为 0.215。故须 hybrid：向量主信号 + 字面 bigram 辅助。

**② 检索决策全在代码，不在模型。** 完整流程：

```
使用者一句话
 ├─① 硬过滤 ── 这则资料「能不能给」：权限 / 归属 / 审批 / 启用
 ├─② 打分   ── 向量余弦 + 字面 bigram（hybrid）
 └─③ 卡门槛 ── 分数 ≥ floor 才给，低于 floor 就回「书上没写」
```

**门槛是产品决策，不是技术参数**：调低 → 模型手里总有材料但会拿教材泛论硬答（幻觉来源）；调高 → 常回「书上没写」（诚实但可能显笨）。

## A5. 检索成本实测（暴力检索）

| chunks | (a) embedding_json + 逐行 json.loads + Python 余弦 | (b) float32 BLOB + numpy 矩阵 |
|---|---|---|
| 31（本手册） | 5.56 ms | 0.007 ms |
| 200 | 39.82 ms | 0.016 ms |
| 1,000 | 200.17 ms | 0.125 ms |
| 5,000 | 957.26 ms | 0.425 ms |
| 20,000（约 100 本） | 3,816 ms | 1.76 ms |

结论：① 数学上几乎免费（512 维点积）；② 慢的是逐行 JSON 解析（差 2000 倍）；③ 免不掉的「问题→向量」6.8 ms 才是固定成本，相对 LLM 1–2 秒可忽略。

实现决定：向量存 float32 BLOB（512×4 = 2 KB/段）、导入后矩阵载入内存、每轮一次 `matrix @ q`、**不上 ANN**（超过 10 万段再考虑 sqlite-vec / FAISS HNSW）。容量上限、mmap 阈值与 `/health` 指标见 **A8.3**；记忆模块（`memory_chunks.embedding_json`）走的是同一条慢路径，实测数字与改法见 **A8.4**。

# A8. 多文档泛化与容量上限（2026-10-03 v2 新增）

## A8.1 每份文档一份清洗 profile

**为什么**：A6/A7 的清洗判据（目录、图书特色、学习目标、任务描述、填空／选择／判断）是从**这一本**职教教材的体例里长出来的；另外「只提问不给答案的习题式案例练习」这一类（如 315 字的空白表格）是我核对语料时补上的，见 D.1。换第二本书，章节命名、层级深度、习题排布都不一样，同一套全局规则会误杀正文或漏放练习。

**实测依据（本手册，去空白 19,447 字，按父层归属分类）**：

| 类别 | 字数 | 占比 |
|---|---|---|
| 知识学习 | 10,519 | 54.1% |
| 实训演练 / 案例练习 | 2,457 | 12.6% |
| 填空 / 选择 / 判断 | 2,145 | 11.0% |
| 学习目标 / 任务描述 | 1,835 | 9.4% |
| 目录 | 1,606 | 8.3% |

同一批规则换一本书就未必成立，所以规则必须**跟文档走**，不能跟代码走。

**怎么改**：

- 新增 `data/knowledge/profiles/<slug>.json`，一个文档一份：

  ```json
  {
    "doc": "老年人沟通技能指导手册-老年人服务与管理-8693-3-图书推介.md",
    "keep_sections": ["老年人服务中的", "实训演练", "案例练习"],
    "drop_sections": ["目录", "图书特色", "学习目标", "任务描述", "填空题", "选择题", "判断题"],
    "content_shape": { "drop_pure_exercises": true, "min_chars": 30, "max_chars": 600 },
    "kind_rules": { "scenario": ["老年人服务中的", "实训演练"], "reference": ["知识学习"] },
    "floor_overrides": { "scenario": null, "reference": null }
  }
  ```

- 导入器按 profile 过滤、切分、分档；**没有 profile 的文档默认拒绝导入**（宁可报错，也不要无规则灌库）。
- 两段筛选的分工：`keep_sections` 先按标题粗筛，`content_shape` 再按内容形态精筛——例如「案例练习」整体保留，但其中只提问不给答案的段落由 `drop_pure_exercises` 丢掉。
- `data/knowledge/profiles/` 与 `data/knowledge/calibration/` **应当纳入 Git**（只有规则与问题，不含语料原文），这样别人 clone 后拿到同一套筛选与验收标准；`data/knowledge/**/*.md` 若含第三方原文，按 D.5 的口径处理。
- 新文档的第一轮工作只有一件事：写 profile + `--dry-run` 看 keep/drop 理由，**不改代码**。

**验收**：`--dry-run` 逐段打印「保留／丢弃 + 理由 + 最终 kind」，清洗后本手册落在 15–18 个 chunk、约 4,200 字的 scenario 内容（数字可复现，见 A8.6）。

## A8.2 门槛按文档覆盖 + 新语料入库闸门

**为什么**：一个全局 floor 跨书不成立。余弦分布随用语、段长、主题密度整体平移，而已实测「问题 vs 陈述句」的最差间距只有 **0.001**——任何整体平移都会让固定 floor 失效（要么全放进来，要么全军覆没）。

**怎么改**：

1. `floor_scenario` / `floor_reference` 允许被 profile 的 `floor_overrides` 覆盖（默认沿用全局值）。
2. 增加**入库闸门**：每份新文档必须配一份 `data/knowledge/calibration/<slug>.jsonl`（同一套 12–15 组「场景问题 → 期望命中的 section_path」），跑完满足**命中率 ≥ 80% 且命中带与未命中带不重叠**才允许入库。不达标就先把文档改写成场景形态，或者放弃这份语料——**不要靠调低 floor 硬塞**。
3. 校准结果（每一问的 top-1 分数与命中段落页码）写进导入报告，并让 `/health` 暴露 `knowledge_calibration`（每文档通过与否）。

**验收**：一张分布表 + 一份闸门结论；「奶奶不吃饭怎么劝」这类手册没写的问题必须回「书上没写」，而不是拿教材泛论硬答。

## A8.3 容量上限与 mmap 阈值

**实测依据**：

- float32 = 512×4 = **2,048 B/段**常驻内存 → 2 万段 41 MB、10 万段 205 MB。本机是 16 GB 笔记本且服务常驻约 1.4 GB，当前可用仅约 2 GB，所以内存不能按「语料无限增长」来假设。
- numpy 暴力检索：31 段 0.007 ms → 20,000 段 1.76 ms（近似线性）；固定成本是「问题→向量」6.8 ms，LLM 1–2 秒。所以到 10 万段（约 9 ms）都还不需要 ANN。

**怎么改**：

- 段数 ≤ **20,000**：常驻 numpy 矩阵，每轮一次 `matrix @ q`。
- 段数 > 20,000：导出 `knowledge_matrix.npy` + `knowledge_ids.json`，用 `np.load(mmap_mode="r")` 让 OS 分页，RSS 不随语料增长。
- `/health` 增加 `knowledge_chunks`、`knowledge_bytes`、`knowledge_mode`（`memory` | `mmap`）、`knowledge_calibration`，与已有的 `asr_backend` / `voiceprint_*` 同一风格。
- **重新评估 ANN 的门槛**：> 10 万段，或需要多租户／多维预过滤（那时才考虑 sqlite-vec / FAISS HNSW）。

**验收**：导入 2 万段合成数据，量 RSS 与单轮延迟；`knowledge_mode` 在阈值两侧正确切换。

## A8.4 可选、独立的一步：记忆向量从 `embedding_json` 改成 float32 BLOB

**这不是知识库的一部分**，是顺手发现的同一问题，独立发布、不阻塞 A8.1–A8.3。

**实测依据（用真实的 `rank_chunks` + 真实 `MemoryChunk` 在本机跑）**：

| 池大小 | ms/问题 | 最坏 8 个子问题 |
|---|---|---|
| 32（slot 满） | 4.39 | 35 ms |
| 200 | 24.59 | 197 ms |
| 500（`MAX_CANDIDATES` 上限） | 66.93 | **535 ms** |

- 旧路径的 `json.loads` 逐行解码：500 行 = **123.4 ms**；最坏一轮会加载最多 3 个池（slot+shared / hot / cold）≈ 1,000 行。
- 向量体积：JSON **10,973 B/段** vs float32 BLOB **2,048 B/段**（小 5.4 倍）。
- 合计最坏一轮 ≈ **0.5–0.8 秒纯 CPU**，与 LLM 的 1–2 秒同量级，而且和 ASR 抢同一颗 4 核 CPU。（典型用户只有几十条记忆且池是懒惰加载，日常是几毫秒——问题出在上限被撑满时。）

**怎么改**：migration 增加 `embedding_blob BLOB`（保留 `embedding_json` 兼容读取，写入双写或渐进迁移）；`select_for_turn` 的池改成「每用户矩阵缓存 + 一次点积」，`cosine()` 不再逐段重算范数。

**边界**：必须保持现有测试基线（当前 216 passed / 1 skipped）不退化，尤其 `tests/memory/`；旧库只有 JSON 时必须仍能检索。**结论**：作为独立一步排在第 8 位。

```
标题 h1:1 h2:2 h3:4 h4:20 h5:30   页码锚点 55   图 4   表格行 9

```

**实作中又修掉一个静默丢内容的缺陷**：原先只把「叶子节」变成 chunk，于是**既有正文又有子标题的节**（任务4 的 `知识学习` 导语 115 字、手写文件的标题下引子）会被无声丢弃。现在每个有自有文字的节都参与，纯结构节（只有子标题）因字数为 0 自然跳过，丢弃明细也不再混入这些空节。手册因此从 30 段变成 **31 段**（多出那 115 字的 reference），丢弃清单仍是干净的 24 段。

**顺带修正 A2/B1 的一个说法**：55 个 `<sub>pN</sub>` **全部在目录里**（第 24–78 行），正文没有页锚点。所以出处不是「扫描正文锚点」，而是**从目录建立「章节 → 起始页」映射**（`markdown.assign_pages`，同名标题按出现顺序一一对应）。实测引用形如 `沟通手册 p18 › 二、老年人服务中的语言沟通`。诚实的限制：页码是该**节的起始页**，不是每个 chunk 的精确页。

**另一个修正**：A6/A7 的判据只按标题筛，会把「只提问不给答案」的习题当资料——例如 330 字的空白表格、294 字的「奇奇对刘爷爷的印象受到了哪些因素影响？」。现在由内容形态规则拦下（`empty_table_to_fill` / `questions_only` / `task_instructions` / `question_tail`）。反过来，原先被我判为「噪声」的 `课后练习 › 四、案例练习` 里有真实的老人口语场景（李爷爷的药、陈奶奶听力不好、小王边接电话边整理文件），现在作为 scenario 保留——这正是「按内容判、不按标题判」的价值。

## A9.7 扫描书 OCR 落地（2026-10-03 v4）

### A9.7.1 页码偏移：用页脚 OCR 标定，不靠推断

页脚页码本身能被 OCR 读出来，所以偏移是量出来的而不是猜的：

| 书 | 采样（PDF → 印刷） | 结论 |
|---|---|---|
| A 老年人沟通技巧（251 页） | 40→28、90→78、140→128、180→168、220→208、245→233 | **+12**，前后段一致 |
| B 明明白白你的心（306 页） | 40→30、90→80、150→140、200→190、250→240、290→280 | **+10**，前后段一致 |

> 教训：「从目录页数页码推断偏移」是错的——最初推断 B 是 +6，实测是 +10，差 4 页；照着错偏移 OCR 会整段错页。

### A9.7.2 工具选择与真实体积（实测，不是估价）

用 `pip install --dry-run --report` + PyPI wheel 大小量：

| 新装 | wheel |
|---|---|
| opencv-python 5.0.0.93 | **46.1 MB** |
| rapidocr-onnxruntime 1.4.4 | 14.2 MB |
| shapely / pyclipper / six | 1.7 MB |
| **合计** | **62 MB 下载**（解压后约 80–90 MB；模型已打包） |

**不引入 torch、也不引入 paddle**（依赖解析结果里没有它们）。这很重要：PaddleOCR 要拖 paddlepaddle CPU 轮子（100–500 MB）。**ONNX 路线复用了项目已有的 onnxruntime。**

### A9.7.3 速度与限流

- 150 DPI，CPU-only：**5.9–13.5 秒/页**（正文页约 10–13 秒，空白/扉页 2 秒）。换算：60 页 ≈ 10 分钟、163 页 ≈ 30 分钟、557 页 ≈ 90 分钟。
- 引擎默认 `intra_op_num_threads: -1`（吃满所有核心），而服务的 ASR 设了 `ASR_CPU_THREADS=8`，两者会抢同一颗 4 物理核 CPU。**`scripts/ocr-book.py` 默认限 4 线程**（`--threads`），实测占用约 3.8 核；OCR 期间服务 `/health` 正常、知识库段数不变。

### A9.7.4 字准率闸门（10 页逐字比对）

以视觉模型作独立读者，逐页比对（忽略空白与页眉页码）：

```

p286 97.6%  p289 98.9%  p292 98.2%  p295 99.1%   平均 97.9%
```

- p271 是只有标题的章节扉页（12 字样本），不计入。
- 「掉字」里每页约 7–9 字是**我们主动删掉的页眉与页码**（比对基准把它们算进去了），所以**正文净准确率约 98.5%**。
- 错误类型已量化并做成修正表：**入→人 ×6**（进人/深人/人眠）、全角括号被识别成半角 ×7、候→侯、自已→自己、作票→作祟。规则只替换「错形本身不是词」的二元组，**不做单字替换**。

### A9.7.5 实作中修掉的四个缺陷

1. **页码标记混用**（有的用印刷页、有的用 PDF 页）→ 统一为印刷页，`--offset` 可指定或自动侦测。
2. **标题误判**：换行句子的尾巴（「重要原因」）被当成 `###` 标题 → 现在要求上一行必须句末，且居中或有额外间距。
3. **段落合并完全失效**：用「行间空白」当中位数，而 OCR 文字框会重叠 → 中位数≈0 → 几乎每行都成一段。改用**行距中位数**后，每行=一个完整段落。
4. **跨页断句**：页尾未结句的文字现在并入下一页首段（沿用 `pdf_to_md.py` 的承接规则）。
5. 另加**页眉识别**（同一文字在 ≥3 页顶部重复即删除）与**开头文字不再静默消失**（第一本手册的丢弃数因此从 24 变 25，多出的是 162 字封面元数据）。

### A9.7.9 尝试一：probe（**实测否决，保留为可选**）

原因不是门槛，而是**信号本身太弱**：chunk 存的是**陈述句**，用户问的是**问句**，而本项目早就量过「问题 vs 陈述句」的最差间距只有 **0.001**（记忆飞轮当初就是靠 **probe**——为每则记忆存一个「它会回答什么问题」的规范问句——才把这条缝隙拉开的：问题 vs 问题的间距是 0.215）。

于是按记忆模块的做法实现：migration v7 加 `probe` 列、`scripts/generate-probes.py` 用 LLM 批量生成规范问句（示例质量：「我照顾老人时，沟通到底是怎么回事啊？都包括谁在说、说什么、用什么方式说、在什么环境下说这些吗？」）、把 **probe 的向量**存进 `embedding`，`score_chunk()` 原样工作。

**结果与预期相反（这是可复现的反证，全部实测）：**

| 变体 | 全域命中 | 命中带最低 / 真负例最高 | 餘量 | 手册 | A | B |
|---|---|---|---|---|---|---|
| 語句向量（基線） | **24/28（86%）** | 0.6243 / 0.6226 | 0.0017 | 100% | 71% | 100% |
| probe 向量 | 21/28（75%） | 0.3264 / 0.5952 | ✗ 重疊 | 82% | **79%** | 33% |
| 標題＋語句 | 23/28（82%） | 0.6175 / 0.6083 | **0.0091** | 100% | 71% | 67% |

probe 只对 A 略好（71%→79%），却把手册（100%→82%）和 B（100%→33%）拉低——因为**生成出来的 probe 是「照护者口语」风格，而校准问题是「什么是 X」风格**：换了错配对象而已。记忆飞轮能work，是因为那里的 probe 来自用户自己的原话、查询也来自同一个人，风格天然一致。所以 probe 现在是**可选**（`import-knowledge.py --with-probes`，快取留在 `data/knowledge/probes/`），默认仍用语句向量。

另外试过**标题增强**（把节标题拼进被嵌入的文本）：余量 0.0017 → 0.0091（5 倍），但少 1 个命中，B 掉到 67%，同样不采用。

### A9.7.10 真正的修复：页码继承（cleaner v3）

看清排名后发现问题被我自己放大了：「爷爷得了老年痴呆」的**正确段其实排在第 2、第 5**，只是它们 `page=None`（段落起始页没有继承页锚点），于是按页范围匹配被判成 MISS。

修法：chunk 缺页码时继承**文档中最近一次见到的页锚点**（分页文档里页码不该是「未知」）。重导后三份文档 `page=NULL` 全为 0，闸门随即变成：

```
手册 11/11（100%）✓   A 12/14（86%）✓   B 3/3（100%）✓
全域 26/28（93%）  命中带最低 0.6243 > 真负例最高 0.6226 ✓ 不重叠
```

### A9.7.12 收尾状态与仍存在的两个缺口（含重排器的实测否决）

- 服务已重启：`/health` 报 `chunks=341`、`floor=0.623`；三份文档 `calibration_status=passed`。
- 仍有两题「书里有、检索排不上来」：**「奶奶不肯吃饭怎么劝？」**（正确段在 226–234，实际 top-1 落在 p91）与**「老人做了手术一直很怕」**（应为 141–148，实际 p225）。端到端表现为模型回答「手冊裡沒有直接寫…」并给出通用建议——**诚实但不理想**。
- 余量 0.0017 很薄：门槛能分开，但没有安全边际。
- **试过 LLM 重排器（`services/knowledge/rerank.py`，migration 无关，纯加一个可选阶段），实测数据如下：**

| 配置 | 旗舰题结果 | 单题耗时 |
|---|---|---|
| 池=20（能覆盖 rank 12–15 的正确答案） | **正确**（选出 p234/p229/p227） | **13.4 s** |
| 池=20，模型输出被 reasoning 吃光后重试 | 另一题为 `no_json`，45.2 s 后回退 | **45.2 s** |
| 池=6 / 8（快） | **答对不了**：正确答案在 rank 12–15，池子根本装不下 | 4.1–5.2 s |

结论：**它确实能修好旗舰题，但代价是每轮不确定查询 13–45 秒**——对一个陪伴对话不可接受；池子缩小到能接受的速度就看不见答案。因此 `IOT_KNOWLEDGE_RERANK` **默认 0**（关闭），代码与测试保留（`tests/knowledge/test_knowledge_rerank.py` 5 个用例覆盖解析、重试、`[]` 与失败的区别），留作离线校准与将来接本地 cross-encoder 的骨架。

### A9.7.13 尝试三：句子滑窗最大相似度（**同样实测否决，保留开关**）

思路来自本项目自己量过的现象——把多个主题平均进一个向量会拖低相似度（记忆模块实测 0.7172 → 0.5898）。做法：把每个 chunk 切成约 90 字的**句子对齐滑窗**（1602 个窗，schema v8 存 `windows` BLOB），chunk 的分数取「整段余弦」与「最佳窗余弦」的较大者（`score_chunk(..., embedding_override=)`，评分函数本身不变）。

```
命中帶整體上移：手冊 0.6395→0.6818   B 0.6855→0.7599   A 0.6243→0.6463
真負例最高也上移：0.6226 → 0.6406
餘量：0.0017 → 0.0057（3.4 倍）
但 A 掉一題：86% → 79%（低於 80% 閘門），全域 93% → 89%
```

失败的正是「爷爷得了老年痴呆」：窗口把**无关段**（手冊 p12「沟通的层次」）推了上来——对一个 max over 5 倍向量数量的打分来说，假命中的机会同样变成 5 倍。试过「只对已选池重排、不改池子选择」，结果相同（25/28）。因此 `IOT_KNOWLEDGE_WINDOWS` **默认 0**；代码、存储与测试保留（`tests/knowledge/test_knowledge_windows.py`）。

**三次尝试（probe 向量、LLM 重排、句子滑窗）都没能提高 A 的命中率**——每次都是用一题换另一题。这说明瓶颈在 **bge-small-zh（512 维）在这份语料上的判别力**，不在流水线。

### A9.7.14 本地 cross-encoder：这台网络拿不到模型（**需要你决定**）

原计划是接一个本地 cross-encoder（20 个候选约 50–200 ms、确定性、不上传）。实测网络：

| 站點 | 結果 |
|---|---|
| huggingface.co / hf-mirror.com | **ConnectTimeout**（无代理，环境变量也没有代理设定） |
| modelscope.cn | **HTTP 200 可達** |
| ModelScope `Xenova/bge-reranker-base` | 只有 tokenizer 與 `quantize_config.json`，**ONNX 目錄被鏡像丟掉** |
| ModelScope `BAAI/bge-reranker-base` | **只有 PyTorch 權重**：`model.safetensors` / `pytorch_model.bin` 各 **1,060 MB** |

所以「小而快的 ONNX cross-encoder」在当前网络下取不到。剩下两条路，都需要你选：

1. **下 1,060 MB 的 PyTorch 權重 + 依賴 torch 跑 cross-encoder**（torch 這台機器已裝，但本項目已把 torch 列為**可選**（`requirements-voiceprint.txt`）：base 安裝沒有 torch）。代價：1 GB 下載、KB 級別的啟動記憶體、每輪 20 對推論（預估 1–3 秒），以及「知識庫重排需要 torch」這個新的可選依賴。
2. **維持現狀**：全域 26/28（93%），A 86%、B 100%、手冊 100%，餘量 0.0017。兩題仍然落在「書裡有、排不上來」。

### A9.7.15 本地 cross-encoder 落地：下载、接线与实测（**默认关闭，开关保留**）

选了路线 1（下 PyTorch 权重、让知识库依赖可选 torch），做完并实测。结论先说：**能提高召回，但不能开**——它会把一个本该答「手册里没写」的问题，答得和真命中一样自信。

**一、下载与体积**（`scripts/download-rerank-model.py`，可重跑，`--check` 只校验不下载）

| 项目 | 实测 |
|---|---|
| 来源 | ModelScope `BAAI/bge-reranker-base`（HF 与 hf-mirror 在本机 ConnectTimeout） |
| 文件 | 6 个，`model.safetensors` 1,112,206,140 B（**1,060.7 MB**），逐个 SHA-256 记进 `models/manifest.json` |
| 新依赖 | transformers 5.18.0 + safetensors 0.8.0；torch 2.14.0+cpu 本机已有（`requirements-voiceprint.txt` 的可选依赖） |
| 加载 | 14.3 s（一次性，懒加载；不启用则不加载） |

**二、接线**（`services/knowledge/rerank.py`、`retriever.py`）

- `IOT_KNOWLEDGE_RERANK=local|llm|0`（默认 `local`，但 `rerank_enabled` 默认 **假**，所以默认路径不变）、`..._RERANK_BELOW`（触发阈值）、`..._RERANK_KEEP`、`..._RERANK_FLOOR`（第二阶段准入）、`..._RERANK_MAX_LENGTH`。
- `retrieve(..., trace=)` 回报第二阶段判定（`reranked` + 每个 chunk 的重排分），校准脚本据此量出**重排带**——因为第二阶段已启用时，准入用的是重排分而不是混合分。
- `/health` 报 `available` 与失败原因；模型目录缺失或 torch 缺失时只是降级，服务照常启动。

**三、实测中发现并修掉的缺陷**：`--rerank-keep 5` 只传到了 settings，**没传进重排器对象**（它内部固定 keep=3），于是排在第 4 名的正确段被自己截掉——「奶奶不肯吃饭」与「老人和家里人吵架」同时判 MISS。修法：`rank()` 返回**完整排序 + 分数**，由调用方按 `rerank_keep` 截取、按 `rerank_floor` 准入。

**四、关键实测**（28 正例 + 6 负例，`--rerank local --rerank-keep 5`）

| 配置 | A(14) | B(3) | 手册(11) | 全域 | 命中带 vs 负例带 |
|---|---|---|---|---|---|
| 关闭（现状） | 12/14 (86%) | 3/3 | 11/11 | 26/28 (93%) | 0.6243 / 0.6226 ✓ 余量 0.0017 |
| 打开，`max_length=256` | **13/14 (93%)** | 3/3 | 11/11 | **27/28 (96%)** | 混合分 0.6161 / 0.6226 ✗；重排分 **−1.67 / +1.53 ✗** |
| 打开，`max_length=512` | 12/14 (86%) | 3/3 | 11/11 | 26/28 (93%) | 混合分 0.6161 / 0.6226 ✗；重排分 **−0.05 / +1.71 ✗** |

- 修好 keep 后「奶奶不肯吃饭怎么劝？」**变成命中**（正确段进入注入集；不过它的 top-1 仍是 p91「拓展学习」，重排器的排序并不干净）。
- 唯一剩下的未命中仍是「老人做了手术一直很怕」：正确答案（印刷 141–148）**根本不在 20 个候选池里**，重排器看不到它——这是池子问题，不是排序问题。
- **第二阶段不可分，且比第一阶段更糟**：正例最低 logit −1.67，负例最高 +1.53，**相隔 3.2 个 logit 还是重叠**。抬高准入阈值会先丢掉命中（例如「老人说人活这么长」的正确段只有 −1.65），却挡不住负例（+1.53）。**没有任何阈值能同时做到两件事**，两个窗口长度下都如此，所以这不是截断造成的。
- 换句话说：重排器确实"知道"有些段落更相关（正确段常见 +2～+6），但它对**不相关**的段落同样会给高分（错段 +3.05/+3.59/+4.77 都出现过）。

**五、速度**（4 核 8 线程笔记本，20 个候选）：fp32 **8.1 s @256**、**12.1 s @512**；int8 动态量化 5.6 s（未接入）。触发条件是 top-1 混合分 < `rerank_below`（默认 0.70），而这份语料的命中分大量落在 0.62–0.70，所以**大多数回合都会触发**。真实回合实测：`IOT_KNOWLEDGE_RERANK=local` 下问「老人和家里人吵架了，来跟我诉苦，怎么接话？」，整轮 **22.2 s**（同一问题在不启用时约 4–5 s）——因为 `split_queries` 会把一句话拆成多个子问题，**每个子问题各跑一次重排**，8 s 是单个子问题的价格。

**六、决定**：`IOT_KNOWLEDGE_RERANK` **默认 0**。理由不是"不 work"（召回确实 26→27），而是**用了会把负例答得和真命中一样自信**，正是闸门要防的事；加上整轮 22 s 的延迟。开关、manifest、bootstrap `-WithRerank`、单测（`test_knowledge_rerank.py` 新增 8 例覆盖 `rank`/准入/keep/trace/环境选择/模型缺失降级/stats 诊断）全部留好，等换判别力更强的 embedding 或更小的 ONNX 重排器时可直接启用。`/health` 会报 `knowledge_reranker` 与诊断原因（缺包或缺权重时不是静默降级）。

### A9.7.16 校准方法学的修正（这次踩到的坑）

最初把「负例」写在每份文档的校准文件里，并按文档分别计算「命中带 / 未命中带」。这在**共享索引**下是错的：

- 第一本手册的旧负例「奶奶不肯吃饭怎么劝？」在第一本之后加入 A 书后，**已经被 A 书合法覆盖**，留着它计算出来的「未命中带」毫无意义；
- 「书里没有、就该回没有」与「书里有、但没排上来」是两种不同的失败，前者是**门槛**问题，后者是**检索质量**问题——混在一起算，就会把失败正例的 0.68 与命中带的 0.62 相比，得出「两带重叠」的假结论。

现在的做法：**正例按文档存、负例单独一份 `_negatives.jsonl`、闸门做全局**，并把失败正例单独列出。

### A9.7.17 真实回合暴露的两个提示词缺陷（2026-10-03 已修，含前后对比）

用户实测的一轮对话：

```
你：和老人如何讲话？
机器人：和長輩說話，確實需要多一分耐心與體貼，這份用心本身就很不容易。手冊裡有幾個實用原則
        （《溝通手冊》p18）：說話簡明、一次別給太多資訊；多傾聽，不急著打斷；重要的事可以
        重複，或寫下來幫忙記憶。若長輩聽力較弱…（《溝通技巧》p121）。一個可執行的小建議：…
```

两个缺陷，都不是检索问题，而是**注入提示词自己招来的**：

1. **来源标签漏进嘴里**。`pipeline.py` 的知识块原文写着「可自然帶出頁碼或章節」，而 `render_context()` 又把出处渲染成 `[不可信參考 溝通手冊 p18] …`——模型照抄，于是陪伴机器人把页码念了出来。修法：知识块改为「**不要提到書名、手冊、頁碼或『節錄』這些來源字樣，也不要逐字複述或條列**」，并新增 `render_excerpts()`：**注入正文时不带来源标签**（出处仍然作为 `citations` 回传给前端，Dashboard 照常显示），所以模型即使不听话也无从抄起。
2. **没有长度上限**。系统提示只说「簡潔」，于是 4 段手册节录被逐条复述成 4 句以上。修法：系统提示写进口语上限——「這是面對面說話，不是寫文章：整段回覆以 **2～3 句、約 60 字**為上限（英語約 40 詞），不要條列、不要朗讀清單、不要複述使用者的整句話；只有涉及安全或風險時，才多說一句必要的提醒」，知识块再加一条「只取最相關的一到兩點，融進那 2～3 句裡」。

**改后实测**（同一台服务、同一批问题，HTTP `/api/chat` 原样记录）：

| 问题 | 修复前 | 修复后 |
|---|---|---|
| 和老人如何讲话？ | ~130 字、4+ 句、含「（《溝通手冊》p18）（《溝通技巧》p121）」 | **69 字、2 句、无来源字样**，citations 仍回传 4 条 |
| 老人晚上睡不着… | — | 71 字、2 句、无来源字样，`emotion=negative` |
| 怎么给汽车换轮胎？（无关） | — | 59 字、**citations=0**，不假称手册里有 |

测试同步收紧（`tests/knowledge/test_knowledge_retrieval.py`）：原来断言 prompt 里**必须**出现 `[不可信參考 溝通手冊 p18`，现在反过来断言**不得出现来源标签**、但 `result.citations` 必须带上它；另加一条断言系统提示含长度上限。全套 **260 passed / 1 skipped**。

## B2. 认同的决策

1. **不引入向量库 / RAGFlow / ANN / cross-encoder** —— 31 个 chunk 的量级，暴力余弦是微秒级，引入那些是过度工程。
2. **向量存 float32 BLOB，不用 embedding_json 逐行 json.loads** —— 性能洞察正确，且顺带发现了现有记忆系统（`embedding_json` 慢路径）的同一问题。
3. **必须 hybrid（向量 + 字面 bigram）** —— 项目已实测「问题 vs 陈述句」余弦间距只有 0.001，纯向量确实废。
4. **门槛是产品决策，不是技术参数** —— 这是最该由使用者拍板的点。
5. **与记忆系统分开建表** —— 存储分离合理。

## B3. 提醒 / 补充

**1. 最大的风险不是工程，是语料本身。**

这份是**职教教材**，不是「应答手册」。结构是：图书特色 → 目录 → 学习目标 → 任务描述 → 知识学习 → 实训演练 → 课后练习（填空 / 选择 / 判断 / 案例练习）。对陪伴机器人真正有用的只有「知识学习」和「案例练习」，其余全是噪声。且正文是**概念性书面语泛论**（如「沟通的过程：发送者→编码→渠道→解码→接收者」），不是「遇到 X 场景，这样说」的可操作话术。

用户问「奶奶不吃饭怎么劝」，检索到「沟通的因素」是没用的。方案也承认「泛论硬答」风险，但这事的优先级**高于**检索技术选型。

**2. 嵌入模型必须复用现有的，别另起炉灶。**

方案写「bge-small-zh-v1.5，90MB ONNX，512 维」——但这个模型**项目里已经装好了**：

- `models/manifest.json` 有 `memory.bge-small-zh-v1.5`；
- `app.py:144` 已在 `providers.get("embedding") or create_embedding_provider()`；
- `services/memory/embeddings.py` 已封装 `OnnxEmbeddingProvider`，含 `embed_documents()` / `embed_queries()`、query 前缀、CLS pooling、L2 归一化。

knowledge 侧应**直接注入同一个 embedding provider**，而不是再写一套。

**3. 检索打分逻辑复用，别重写。**

`services/memory/retriever.py` 已有 `score_chunk / rank_chunks / retrieve`（含 floor 门槛、`lexical_similarity`、bigrams），`services/memory/` 下还有 `recall.py / candidates.py`。「与 memory 分离」应指**存储分离**，但**检索代码可复用**，只换数据源（`knowledge_chunks` 而非 `memory_chunks`）。

**4. 口语 + 繁简问题，比方案讲得更严重。**

机器人是粤语 / 繁体**口语**场景，教材是简体**书面语**，查询还是 ASR 转写的口语。方案提的「繁简各查取最高」只是字符换算，解决不了「口语 vs 书面语」的语义鸿沟。要么接受「只对书面提问有效」，要么对语料做一轮口语化改写 / 同义扩充，否则命中率会很差。

**5. `ragflow.py` 建议「标记未实现」，而不是删掉。**

接口不匹配是真的，但删掉会丢掉与上游 xiaozhi 对齐的参考。保留并加注「未来可选、需适配 retrieve 接口」更稳妥。
