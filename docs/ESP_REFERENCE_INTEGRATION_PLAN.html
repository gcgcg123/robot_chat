小智 ESP32 參考整合與模擬 ESP 改良方案

專案：IoT 情感陪伴機器人　|　版本：2026-09-14

參考資料：v2.5.0_alientek-atk-dnesp32s3（編譯韌體）及 xiaozhi-esp32-2.5.0（完整原始碼）。

一、整合原則

小智是 ESP 韌體與通訊參考；我們的 Python 後端、情緒分析、聲紋、使用者管理和 Dashboard 是本專案核心。整合會採用相容的事件概念，保留自己的資料模型和安全邊界，避免直接把小智 server 或預設 AI 服務當成我們的產品邏輯。

ESP 麥克風／按鍵 → WebSocket session → 後端接收 audio 或文字事件 → ASR → 聲紋識別 → 情緒／風險分析 → DeepSeek → TTS segment + display.state → ESP LCD 字幕、表情、播放

四、目前模擬 ESP 的改良規格

模擬器不是一般聊天頁，而是用來預覽未來 ESP LCD 的狀態。畫面固定包含裝置外框、LCD 區域、狀態燈、表情圖像、字幕區、音量 meter 和播放中的 segment 指示。

turn.started → listening + 清空本輪字幕 stt.final → transcribing + 顯示使用者字幕 turn.processing → thinking + 思考動畫 tts.segment → speaking + 逐段字幕 + 播放／進度 tts.end → idle + 保留最後回覆 turn.failed → error + 可重試提示 heartbeat stale → offline + 連線提示

長字幕會以 LCD 寬度估算自動換行，最多顯示固定行數；新 segment 到達時只更新必要區域，避免畫面閃爍。

五、第二階段才接真 ESP 的項目

項目原因
第二階段 DNESP32S3 GPIO、LCD controller、I2S 麥克風／Codec要以實際 PCB 和 2.4 吋 LCD 型號核對，不能只靠 Release 檔名猜測。
第二階段 韌體編譯、燒錄、Wi-Fi 配置、OTA需要 ESP-IDF、USB 驅動和實體裝置。
第二階段 真音訊串流、播放打斷、LCD 效能需要量測實機延遲、PSRAM、記憶體和音訊時序。
第二階段 MQTT／UDP bridge先完成 WebSocket 端到端，再加入控制面與局域網傳輸，降低除錯範圍。

六、驗收標準

  1. 模擬器可依 WebSocket 事件顯示 listening、thinking、speaking、idle、error。
  2. 使用者語音字幕、機器人回覆字幕和表情狀態同步更新。
  3. 長句自動換行，不溢出 LCD 模擬區域。
  4. 切換使用者或語言時，不會沿用上一輪表情、字幕或聲紋登記狀態。
  5. 服務中斷或 heartbeat stale 時，模擬器明確顯示離線狀態。
  6. 真 ESP 接入前，不把未核對的 GPIO、LCD controller 或韌體 binary 當成已支援。
這份報告中的「直接參考」代表沿用概念、介面順序或工具方法，不代表把小智的程式碼、服務或授權內容原封不動放入我們的產品。

七、改造順序

  1. 建立 display event contract。
  2. 讓後端 WebSocket 在 turn、STT、TTS 節點發出 display state。
  3. 改造 Canvas 模擬器為實體 LCD 視窗。
  4. 加入字幕分頁、表情動畫、音量和播放進度。
  5. 補測試與文件，然後才接真 ESP 韌體。
